# 同一份材料，五级表达方式

共同依据：[自拟教学材料](source.md)。这里展示**路由选择**，不是要求每次生成五份答案。

## 1. Text：解释名称、机制与证据

用户问：“帮我看懂这个资料处理器，检查通过是不是就能相信结果？”

参考回答：

检查通过，只说明文件格式和访问权限都满足要求。它还没有证明生成的解释正确。

资料处理器收到文件后，同时检查格式和访问权限。两项都通过，文件才进入处理队列；任一项失败，就返回原因。生成解释时如果发现来源不完整，处理器会暂停这个文件，请求补充材料。材料补齐后才继续生成。

生成的解释最后还要由用户核对。因此，检查通过、解释生成完成和内容核对完成，是三个不同状态。

材料中的初测只有 20 份内部报告。平均阅读时间由 8 分钟降至 6 分钟，减少了 2 分钟，即相对减少 25%。这是一项观察；其他影响因素是否得到控制，材料没有说明。它不能证明变化一定由处理器造成，也不能说明处理论文时同样有效。

**为什么停在 Text：**当前卡点是状态含义和证据边界，不需要为了丰富输出再画图。

## 2. Table：比较容易混淆的状态

用户问：“检查通过、生成完成、人工核对到底差在哪里？”

| 状态 | 已经完成什么 | 仍然不能说明什么 |
| --- | --- | --- |
| 检查通过 | 格式与访问权限都通过 | 不能证明内容正确 |
| 生成完成 | 系统已经产出解释 | 不能证明用户已经核对 |
| 人工核对 | 用户完成内容检查 | 材料没有定义更高一级的认证 |

**为什么用 Table：**三个对象存在相同比较维度。如果改成长段落，读者需要来回找差异。

## 3. Diagram：看清同时发生、全部满足与返回路径

用户问：“检查和生成是怎么衔接的？画出来。”

使用 [流程图](flow.svg)，配一句说明：格式与权限同时检查，必须都通过才进入处理队列；材料不足时暂停，补齐后返回解释生成环节。箭头表示处理先后或条件流转；横向并列的两项检查表示同时进行。

图只展示流程。阅读时间的试验范围和文件损坏原因不属于图内机制；用户问及证据或故障时回到原材料解释，不根据流程猜测。

**为什么是 Flowchart：**问题包含并发、AND 条件、失败分支和反馈回路；架构图或表格都会丢掉关键关系。

## 4. Interactive：观察条件变化

用户问：“文件多一点、同时处理的数量多一点，耗时会怎么变？”

使用 [并行处理教学页面](parallel-demo.html)。页面持续标明教学假设，并区分“生成耗时”和“阅读时间”。默认 N=10、C=3、d=2，分四批，生成耗时为 8 分钟。

把 C 改为 5 后，分两批，生成耗时为 4 分钟。这个结果只来自教学模型，不是产品性能承诺。批次图随输入变化，显示最后一批可能未装满；文件数为零时显示零批次、零耗时。

**为什么升级到 Interactive：**用户的目标不是看一个固定答案，而是主动改变 N、C、d 形成并行处理直觉。

## 5. Animation / Video：看见一份文件怎样随时间流转

用户问：“流程图我看懂了，但一份文件到底怎样一步一步走？”

有 HTML 动画能力时，可使用 [可播放流程动画](process-animation.html)；制作视频时参考 [动画 / 视频 storyboard](animation-storyboard.md)。动画先展示文件进入，再同时进行两项检查，之后根据 AND 条件进入队列或返回失败；来源不足时暂停并形成补材料回路；最后区分“生成完成”和“人工核对”。

**为什么不是再做一张图：**用户已经理解静态结构，卡点是时间与状态演化。动画每一帧只增加一个主要变化，比不断叠加静态箭头更容易形成过程感。

宿主没有动画/视频能力时，交付 storyboard、scene list 或可播放 HTML，不声称已经渲染视频。
