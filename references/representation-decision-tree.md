# 表达形式决策树

目的：选择**最小充分表达**。不是要求每次依次生成五种输出。

## 1. 总决策树

```text
开始
  │
  ├─ 主要卡点是单个概念、论点、证据或边界？
  │      └─ 是 → Text
  │
  ├─ 需要比较两个以上对象，而且存在共同维度？
  │      └─ 是 → Table
  │
  ├─ 理解依赖“关系”而不是“定义”？
  │      └─ 是 → Diagram Type
  │              ├─ 组成/模块 → Architecture / Block
  │              ├─ 顺序/条件/失败返回 → Flowchart
  │              ├─ 多角色交接 → Swimlane
  │              ├─ 分类/层级 → Tree / Hierarchy
  │              ├─ 因果/反馈 → Causal diagram
  │              ├─ 数据移动 → Data-flow diagram
  │              ├─ 时间演进 → Timeline
  │              ├─ 多对多连接 → Network graph
  │              └─ 数值趋势/分布 → Chart
  │
  ├─ 用户需要主动改变输入、条件或情景来形成直觉？
  │      └─ 是 → Interactive
  │
  └─ 理解关键是“随时间发生什么”，静态图仍不够？
         └─ 是 → Animation / Video
```

如果多个条件同时满足，选择能直接解决当前卡点的最低一级。用户明确指定形式时优先满足，但若指定形式会扭曲信息，要指出限制并选择安全替代。

## 2. Text：解释最少但关键的内容

### 适用

- 一个名词、概念、命题、段落或公式含义。
- 需要补“为什么这一步能到下一步”的中间机制。
- 主要问题是范围、概率、证据强度、相关/因果区别。
- 用户要快速判断“我应该怎样理解这句话”。

### 不升级的条件

Text 已能让用户说清：对象是什么、怎样运作、边界是什么。此时不要为了丰富输出再做图。

### 升级信号

- 读者需要频繁来回找 A/B 差异 → Table。
- 出现多个节点、箭头、顺序、分支或层级 → Diagram。
- 用户问“把 X 改成 Y 会怎样” → Interactive。
- 用户说“我知道步骤，但脑中看不到过程” → Animation/Video。

## 3. Table：减少比较时的工作记忆

### 适用

至少有两个对象，并且可以使用同一组比较维度，例如：

- 模型 A / B / C 的输入、输出、训练目标、优缺点。
- “检查通过 / 生成完成 / 人工核对”三个状态的含义。
- 证据类型、支持范围、不能推出什么。

### 表格设计规则

1. 每一行或每一列只表达一个稳定维度。
2. 未知写“材料未说明”，不要留空让人误以为“没有”。
3. 比较维度少于两个时通常不需要表格。
4. 流程顺序不是表格的强项；有分支、回路、并发时转 Diagram。
5. 数值多且趋势比具体数字更重要时，用 Chart 而不是大表格。

## 4. Diagram Type：先判断关系，再选图

### 4.1 Architecture / Block diagram

**问法：**“它由什么组成？”“模块之间怎样连接？”

适合：系统组件、上下游、层级模块、输入输出接口。

避免：用架构图表达严格时间顺序或因果强度。

### 4.2 Flowchart

**问法：**“先做什么？”“什么条件下走哪条路？”“失败后回哪里？”

适合：步骤、判断、AND/OR、错误路径、重试、回路。

必须显式区分：并发 vs 顺序；全部满足 vs 任一满足。

### 4.3 Swimlane

**问法：**“谁负责哪一步？”“不同角色怎样交接？”

适合：跨团队、Agent/人协作、服务间责任边界。

避免：角色只有一个时制造无意义泳道。

### 4.4 Tree / Hierarchy

**问法：**“它属于哪一类？”“父子层级是什么？”

适合：分类体系、组织结构、继承、从属。

避免：把多对多关系硬画成树。

### 4.5 Causal diagram

**问法：**“A 为什么会影响 B？”“反馈回路在哪里？”

适合：有来源支持的因果链、正负反馈、调节因素。

高风险：没有因果证据时只能画“关联/假设关系”，不能用因果箭头冒充证明。

### 4.6 Data-flow diagram

**问法：**“数据从哪里来，经过什么处理，到哪里去？”

适合：RAG、ETL、Agent tool call、API pipeline、训练数据处理。

箭头默认表示数据传递，不自动表示先后或因果。

### 4.7 Timeline

**问法：**“什么时候发生？”“版本怎样演进？”

适合：事件、版本、训练阶段、历史演变。

避免：多个并行因果链只用一根时间线压平。

### 4.8 Network graph

**问法：**“很多对象之间谁连接谁？”

适合：知识图谱、服务依赖、社交/引用网络、多对多关系。

节点太多时先筛选核心子图；“毛线球”不是有效解释。

### 4.9 Chart

根据数据问题选：

| 问题 | 优先图表 |
| --- | --- |
| 随时间变化 | Line chart |
| 类别比较 | Bar chart |
| 分布 | Histogram / Box plot |
| 两变量关系 | Scatter plot |
| 组成占比 | 只有类别很少且总和有意义时才考虑 pie/donut；通常 bar 更易比较 |

图表必须带单位、口径、时间范围和必要的不确定性信息。

## 5. Interactive：从“看答案”变成“操纵模型”

### 触发条件

满足至少一个：

- 用户明确要改变参数或情景。
- 关系存在可计算公式或明确规则。
- 多个条件组合很难靠静态表格穷举。
- 用户需要形成灵敏度、阈值或 trade-off 的直觉。

### 必须说明

- 哪些输入可改。
- 结果怎样计算或转换。
- 依据来自来源、规范、代码，还是教学假设。
- 适用范围和未计入因素。

### 禁止

- 为了“可玩”而发明不存在的公式。
- 只做按钮、滑块和动画，却不改变任何实质结果。
- 把教学模型的输出包装成真实预测。

## 6. Animation / Video：表达时间与状态演化

### 何时优先动画

- 5—12 个离散步骤可以说清。
- 重点是状态变化、对象移动、连接建立/解除、token 或数据流。
- 用户可能需要暂停、重播或逐步播放。

建议结构：

1. 初始状态。
2. 每一步只发生一个主要变化。
3. 当前变化的对象高亮，同时保留前后文。
4. 必要时显示“为什么进入下一步”。
5. 结束时回到完整全局图。

### 何时优先视频

- 需要旁白解释多个场景。
- 需要在“直觉 → 机制 → 例子 → 边界”之间切镜头。
- 单一画布无法承载全部内容。
- 目标是完整教学，而不是单一机制演示。

建议视频结构：

`Hook/问题 → 初始模型 → 分步演示 → 关键转折 → 证据/边界 → 总结`

视频脚本中，事实、类比和教学假设要可区分。不要让旁白补出材料没有提供的因果。

### 能力降级

宿主无动画/视频生成能力时：

- 动画请求 → 提供逐帧 storyboard 或自包含 HTML 动画代码。
- 视频请求 → 提供 scene list + narration + on-screen text + visual instruction。
- 明确“这是制作稿，不是已经渲染的视频”。

## 7. 渐进升级与降级

用户说“还是没懂”时，不是自动进入下一层，而是判断失败原因：

| 失败原因 | 下一步 |
| --- | --- |
| 少了一个中间机制 | 保持 Text，补机制 |
| 对象太多，差异混在段落里 | Table |
| 看不出连接、顺序或条件 | Diagram |
| 看不出参数改变后的结果 | Interactive |
| 看不出时间演化 | Animation/Video |
| 图太复杂 | 降级到局部图或 Text |
| 来源根本没有答案 | 停止升级，明确证据缺口 |

核心原则：**不要用更华丽的形式掩盖信息缺失。**
